# Quotation Section — Assessment & Recommendations

_Date: 2026-05-30 · Reviewer: Claude (Opus 4.8) · Scope: the quotes/quotation
feature across `apps/api` and `apps/admin-web`._

## TL;DR verdict

**The quotation section is genuinely strong — feature-rich, well-tested, and the
newer additions are cleanly built. It does not need a rewrite.** What it needs is
maintenance discipline on a few oversized files and one product decision about a
duplicate engine. Nothing here is on fire; these are the kinds of things that
quietly slow a team down six months from now if left alone.

Two issues are worth acting on soon (cheap to fix, real risk if ignored):

1. **A second, stalled quote engine ("DMC Quote Engine") is live in the main
   nav** — staff can build quotes in the wrong place.
2. **A handful of god-files** (one 14k-line service, several 4–5k-line UI
   components) that concentrate risk.

Everything else is polish.

## What's good (keep doing this)

- **Pricing is properly separated and validated.** `quote-pricing.service.ts`,
  `quote-pricing-validation.ts`, and `multi-currency-pricing.ts` are extracted,
  focused, and backed by real tests (`quote-pricing-scenarios.test.ts`,
  `quote-booking-pricing-integrity.test.ts`, `contract-to-quote-pricing-flow.test.ts`).
  This is the most important part of a DMC quoting system and it's the
  best-structured part of the codebase.
- **Strong test coverage** across pricing, passengers, rooming, booking
  conversion, public links, template expansion, and the guided builder. This is
  what makes the god-files _safe_ to refactor later.
- **The newest layers are exemplary.** `quotes-guided.service.ts` and
  `quote-intelligence.service.ts` are pure read-side services with clear
  contracts, exported pure helpers for testing, and honest "v1 heuristic"
  comments. This is the pattern the rest of the module should converge toward.
- **Proposal rendering is cleanly split** into v2 (legacy pdfkit) and v3
  (Handlebars + Chromium) with a mapper/types separation.
- **The feature surface is impressive**: FIT/GROUP/SERIES, multi-currency + FX,
  FOC, slab/group pricing, hotel option sets, versioning, public client links,
  passengers + rooming, audit trail, guided composition, operational
  intelligence overlay. This is a mature product, not a prototype.

## Issues, ranked by priority

### 1. Two parallel quote engines — decide and consolidate _(high value, low effort)_

> **Status (2026-05-30): DONE except the DB table drop.** The DMC Quote Engine
> has been archived on branch `quotation-section-cleanup`: removed from the nav,
> backend module (`quote-engine.controller/service`) + frontend pages + API proxy
> deleted, and unwired from `app.module.ts`. Verified — API `tsc` clean, nav
> tests 21/21. The `DmcQuote*` **Prisma models + DB tables are intentionally
> retained** (no destructive migration) pending an explicit decision to drop them.

There are **two separate quote systems**:

- **The main `Quote` stack** — the real, production system (14k-line service,
  63 endpoints, deep UI, heavy tests). This is what the business runs on.
- **The `DmcQuote` "DMC Quote Engine"** — a separate model stack
  (`apps/api/src/quote-engine/`, `apps/admin-web/app/quote-engine/`) built in a
  single commit `feat: add DMC quote engine phase 1` (`36a51df`), **never
  iterated since**. You confirmed this was generated by Codex/ChatGPT and its
  status was unknown.

Why this matters: the DMC Quote Engine **is wired into `app.module.ts`, has a
deployed DB migration, and is linked in the main nav** as "DMC Quote Engine"
(`admin-nav.ts:31`). So it's a reachable, half-built parallel path where a staff
member could create a quote that the rest of the system (bookings, proposals,
operations) doesn't fully understand. Two engines also means future quote
features risk being half-built in both.

**Recommendation:** pick one.
- If the main `Quote` stack is the system of record (it clearly is today), treat
  DmcQuote as an experiment: **remove it from the nav now** (5-minute change to
  stop accidental use), then schedule archiving the module + a
  `down`-style migration to drop the unused tables once you've confirmed nothing
  references them.
- If the segment-based multi-country model is where you _want_ to go long-term,
  that's a deliberate roadmap item — but it should then be developed against,
  not left as an orphaned phase-1 next to the real engine.

### 2. God-files concentrate risk _(medium value, medium effort, do incrementally)_

| File | Lines | Notes |
|------|-------|-------|
| `apps/api/src/quotes/quotes.service.ts` | **14,208** | One service doing lifecycle, pricing orchestration, PDF, versioning, templates, passengers, rooming, public links |
| `apps/admin-web/app/quotes/[id]/QuoteItemsForm.tsx` | **5,114** | Single form component |
| `apps/admin-web/app/quotes/[id]/QuoteServicePlanner.tsx` | **4,753** | |
| `apps/admin-web/app/quotes/[id]/page.tsx` | **3,937** | |
| `apps/admin-web/app/quotes/[id]/QuoteAutoItineraryBuilder.tsx` | **2,361** | |

A 14k-line service and 5k-line components are hard to navigate, slow to review,
prone to merge conflicts, and intimidating for anyone new (or for an AI agent
asked to change them safely). The good news: the seams already exist — pricing,
proposals, guided, intelligence, and itinerary are _already_ separate modules.
The same decomposition just hasn't been applied inside `quotes.service.ts`.

**Recommendation:** do **not** do a big-bang refactor. Instead, adopt a
"split-on-touch" rule — whenever you next work in `quotes.service.ts`, extract
the cohesive area you're touching into a collaborator service
(e.g. `quote-versions.service.ts`, `quote-passengers.service.ts`,
`quote-templates.service.ts`, `quote-public-link.service.ts`). The existing test
suite makes each extraction verifiable. Same approach for the big React
components: pull stable sub-sections into child components. The 84 files already
in `quotes/[id]/` show the team knows how to do this — the biggest few just grew
faster than they were split.

### 3. Heuristic-by-regex logic is fragile (but knowingly so) _(low priority)_

The guided/intelligence layers lean on name/keyword regex matching to derive hotel
tiers, activity moods, "popular with groups" notes, recovery-cost destinations,
etc. The code is honest about this ("v1 heuristic", "future PR can replace with
structured tags"). It's fine for now, but it's the kind of thing that silently
mis-classifies as the catalog grows. The right long-term fix is structured
columns on the `Hotel`/`Activity` models (tier, mood, group-friendly flags) so
the logic reads data instead of guessing from strings.

### 4. `(this.prisma as any)` casts bypass type safety _(low priority)_

The guided service accesses Prisma models via `(this.prisma as any).touringRoute`
etc. throughout. This works but throws away Prisma's compile-time safety — a
renamed field or model won't be caught until runtime. Worth understanding _why_
the cast is there (possibly a Prisma client generation / typing gap) and fixing
the root cause so these can be dropped.

## Suggested sequence

1. **Now (minutes):** remove "DMC Quote Engine" from the nav. ✅ _Done — and the
   code is fully archived too (see Status above)._
2. **Soon (a session):** module already archived. Remaining: a `down`-style
   migration to **drop the now-orphaned `DmcQuote*` tables** once you confirm
   you don't want the multi-country model — _or_ explicitly adopt it as a
   roadmap item and rebuild against it.
3. **Ongoing:** apply "split-on-touch" to `quotes.service.ts` and the largest UI
   components. No dedicated refactor sprint needed.
4. **Later:** replace string-heuristics with structured catalog columns; resolve
   the `prisma as any` typing gap.

## Bottom line

This is a well-built, well-tested quoting system that's earned the right to be
trusted. The main risks are _organizational drift_ (a duplicate engine, files
growing past the point of easy review), not correctness. Address the duplicate
engine and keep splitting files as you touch them, and it stays healthy.
